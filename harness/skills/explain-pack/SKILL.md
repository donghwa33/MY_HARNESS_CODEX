# 설명 팩

## 목적
사람이 자기 산출물의 근거, 약점, 장애 대응을 5분 안에 자기 말로 설명할 수 있게 재료를 정리한다.

## 절차
1. README, work/ 의 AGREEMENT·DECISIONS·FINDINGS·REVIEW·EXPLAIN, 제출 문서, git log 를 읽는다.
2. 심사자가 물을 법한 질문 10개를 만든다. 다음 유형을 반드시 포함한다:
   - 핵심 결론의 근거와 반례 (2)
   - 결과에 영향이 큰 데이터 처리 결정의 대안 (2)
   - 조치안·설계의 트레이드오프와 실패 시 대응 (2)
   - 코드·서비스가 새 데이터나 장애에서 깨지는 지점 (1)
   - 방법(보정, 분해)의 가정과 한계 (2)
   - AI 가 제안했고 사람이 수용 또는 기각한 판단 (1)
   - 이 중 2개는 일부러 틀린 전제를 깐 질문으로 만든다 (예: 하지 않은 처리를 했다고 가정).
3. 질문마다 답변 뼈대를 4단으로 쓴다: ⓪ 전제 확인(질문의 전제와 실제 구현의 차이) ① 약점 지점(파일·D/F/R 번호·숫자) ② 위험·파급(어느 방향으로 무엇이 바뀌는가) ③ 다음 검증·개선(행동 + 판정 기준).
   뼈대는 키워드 수준으로 쓰고 완성 문장을 쓰지 않는다. 사람이 자기 말로 채운다.
4. 맨 위에 "가장 약한 지점 3개" 를 한 줄씩 쓴다.
5. work/EXPLAIN_PACK.md 로 저장하고 커밋한다.

## 하지 말 것
- 약점을 축소하거나 빼지 않는다. 약점을 먼저 말하는 것이 모범 답안 구조다.
- 산출물에 없는 내용(하지 않은 분석)을 한 것처럼 쓰지 않는다.
- 메커니즘·이론 설명을 길게 넣지 않는다. 사람이 설명할 수 있는 수준만 쓴다.
