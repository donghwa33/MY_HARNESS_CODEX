# 인터뷰와 합의

## 목적
숨은 정보를 빠짐없이 기록하고, 착수 전에 업무 담당자가 확인한 합의문을 남긴다.

## 절차
1. 과제 README 의 필수 산출물·파일명·형태(보고서/서비스/둘 다)를 먼저 work/STATE.md 에 적는다.
2. 대화 원문에서 질문-답변 쌍을 추출해 work/INTERVIEW.md 표에 기록한다. 답변은 원문 인용, 시각 포함.
3. 각 답변에 태그를 붙인다: [진술] [데이터 확인 필요] [불확실] [미검증] [제약] [리스크]
4. 업무 담당자가 제시한 원인 가설·해법은 "업무 담당자의 가설" 절에 H0 으로 등록한다. 결론으로 쓰지 않는다.
5. 데이터 인벤토리(outputs/inventory.md)와 대조해, 진술과 관련된 열이 있으면 "후속" 칸에 적는다.
6. 합의문은 harness/templates/AGREEMENT.md 형식으로 쓴다. 필수 절: 문제 정의, 검증 대상 가설,
   성공 기준(측정 가능), 산출물과 형태, 만들지 않을 것, 제약, 진행 중 조치, 가정.
7. 업무 담당자에게 보낼 확인 메시지 초안을 5줄 이내로 쓴다. 전송은 사람이 한다.
8. 확인 답변을 받으면 AGREEMENT 상단에 확인 시각과 답변 원문을 적고 커밋한다.

## 누락 확인 체크리스트
- 정의: 지표의 정확한 정의, 기준 기간, 영향 범위, 이미 확인·배제한 것
- 설비(Machine): PM, 부품 교체, 공급사 변경, 레시피, 신규 설비
- 자재(Material): 주요 자재 Lot·공급사 변경
- 방법(Method): 공정 조건, 디스패치·배정 규칙, 작업 표준 변경
- 사람(Man): 교대조, 신규 작업자 (우선순위 낮음)
- 측정(Measurement): 프로그램, 계측 장비, 판정 기준 변경
- 범위: 다른 제품·라인·부서 영향
- 제약: 정지·변경 가능 여부, 용량(CAPA), 실험 가능 여부, 기한, 보안·개인정보
- 산출물: 보고 대상, 형식, 사용 빈도(일회성/반복), 화면·도구 필요 여부
누락 항목이 있으면 사람에게 추가 질문을 제안한다.

## 질문 작성 원칙
- 한 메시지에 질문 4개 이하.
- 막연한 질문 대신 구체 명사로 묻는다 ("변경점 있었나요?" 대신 "10/1 이후 식각 설비 PM 이나 부품 교체가 있었나요?").
- 해법·도구 이름부터 말하지 않는다.

## 하지 말 것
- 답변을 요약하면서 의미를 바꾸지 않는다.
- 합의 전에 분석·구현 코드를 작성하지 않는다 (인벤토리·프로파일링은 예외).
